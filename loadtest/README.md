# Нагрузочный тест подбора и Grafana

Команды запускаются из корня репозитория. Нужны Docker Engine с Compose, GNU Make, Bash и Python 3.10+. Используйте выделенный тестовый Docker-хост и заполните `.env` по `.env.example`. Подготовка каталога рассчитана на пустую тестовую базу.

## Запуск

```bash
make loadtest-prepare
make loadtest CASE=NT01
make loadtest CASE=NT02
```

НТ-01 — контроль функциональности: один измеренный запрос, обычно меньше секунды.
Для нагрузки используйте НТ-02: 10 VU, 60 с разгона, 600 с плато и 30 с спада
(около 11,5 минут). Команда без `CASE` запускает НТ-01. Для короткой проверки
мониторинга: `make loadtest CASE=NT02 HOLD_SECONDS=60`; это проверочный прогон,
а не полный НТ-02 для отчёта.

Ссылка на живой дашборд печатается перед запуском k6. Для НТ-01 смотрите
счётчики и p95 за прогон в верхней строке: графики скорости требуют нескольких
отправок метрик и могут быть пустыми для одиночного запроса.

`loadtest-prepare` поднимает Backend, Matcher, Parser и PostgreSQL. Matcher читает каталог из PostgreSQL. Планировщик парсера выключен. В базу попадают 1 000 синтетических возможностей с seed 42. Повторная подготовка проверяет, что каталог пуст, и прерывается при наличии строк. Для следующего прогона на том же каталоге повторять подготовку не нужно.

`loadtest` запускает Prometheus и Grafana при необходимости. k6 создаёт аккаунты и проверяет идемпотентность до нагрузки. НТ-01 выполняет один измеренный подбор. Переходите к НТ-02 после успешного НТ-01. НТ-02 выводит 10 кандидатов на плато за минуту, держит их 10 минут и завершает нагрузку за 30 с. Каждый кандидат использует отдельную анкету и новый ключ на каждый подбор.

Диагностика выше 10 VU запускается отдельно после НТ-02.

```bash
make loadtest CASE=NT03 USERS=15
make loadtest CASE=NT03 USERS=20  # если стенд выдержал 15 VU
```

Если успешных подборов на плато НТ-02 оказалось меньше 400 из-за малого темпа, проведите отдельный повтор с `HOLD_SECONDS=1200` и укажите его параметры в отчёте.

## Дашборд

1. Откройте [AIESEC Match в Grafana](http://localhost:3000/d/aiesec-loadtest). Для просмотра локального дашборда вход не нужен. Для запуска одного мониторинга выполните `make loadtest-monitor`.
2. Выберите **Прогон** или откройте ссылку из вывода команды. Ссылки сохраняются как `grafana-url.txt` для полного интервала и `grafana-plateau-url.txt` для плато. Точные границы плато указаны в `parameters.txt` в миллисекундах Unix. У всех панелей общая шкала UTC. Выбор фазы «Плато» исключает точки разгона и спада из запросов k6.
3. Сопоставьте активные VU, запросы в секунду, p95 корректного подбора, долю HTTP-ошибок и долю корректных результатов. Окно панелей — 30 с, шаг — 5 с. НТ-01 собирает один замер, поэтому панели, которым нужны несколько точек, могут остаться пустыми. Итоговый p95 и доли для защиты берите из `plateau-report.json`.
4. Для CPU и RAM **до прогона** выполните `make loadtest-monitor-resources`. Команда запускает сборщик Docker Stats API и обновляет конфигурацию Prometheus. Работает с Docker Engine и Docker Desktop/WSL. Сборщик читает CPU и рабочий набор RAM сервисов `backend` и `matcher` проекта `aiesec-match` через Docker socket. Socket предоставляет доступ к Docker daemon; используйте этот стенд локально или на выделенном тестовом хосте. При отсутствии данных проверьте `docker compose -f loadtest/docker-compose.loadtest.yml --profile resources logs docker-metrics` и `up{job="docker-metrics"}` в Grafana Explore. После включения подождите 30 секунд для накопления точек CPU. Панели используют время выбранного прогона: для наблюдения сейчас выберите «Последние 5 минут».
5. Для отчёта откройте полный интервал НТ-02, захватите графики с видимым ID прогона и подпишите время начала и конца плато. При необходимости приложите второй скриншот по ссылке плато.

Если список прогонов пуст, проверьте, прошёл ли `setup()` в `k6.log`, и выполните в Explore запрос `k6_match_started_total`. Метрики поступают из k6 каждые 5 с через Prometheus remote write. Если отсутствует только p95, проверьте `k6_match_wall_seconds` и наличие корректных подборов. [Remote write в k6](https://grafana.com/docs/k6/latest/results-output/real-time/prometheus-remote-write/), [native histograms в Prometheus](https://prometheus.io/docs/prometheus/2.55/feature_flags/).

Артефакты новых запусков лежат в `loadtest/results/runs/`. Сохраните `parameters.txt`, `k6.log`, `raw.ndjson`, `summary.json`, `plateau-report.json` и снимок каталога. Архивные сводки находятся отдельно в `loadtest/results/`.

`make loadtest-stop` останавливает Grafana, Prometheus и сборщик ресурсов. Тома мониторинга и файлы результатов сохраняются. Методика, история порогов и шаблон отчёта находятся в [плане испытаний](../docs/load-test-plan.md).
